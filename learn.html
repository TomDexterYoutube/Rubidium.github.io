Chapter 00

Welcome to
The Rubidium Book

This book teaches two languages from scratch: Rubidium, for application code, and Vire, its companion for binding against real C libraries — no prior systems programming experience required.

Rubidium is a high-performance, statically-typed compiled language designed to be approachable for beginners while scaling to real systems programming. It combines the clean, readable syntax of Python with an explicit, always-visible memory model, and compiles directly to native machine code via LLVM.

Who this book is for

This book assumes you can write basic programs in any language — loops, variables, functions. You don't need to know C, Rust, or anything low-level. If you've written Python, JavaScript, or similar, you'll feel right at home in the first few chapters.

What you'll learn

  • How Rubidium's type system and shared-global memory model work
  • All four collection types — list, index, dict, and dict+
  • Functions, classes, error handling, and the link rule
  • Manual memory management with .drop()
  • Real hardware threading, plus the random/time/os/keyboard/net standard modules
  • How Rubidium's FFI works, and when to reach for Vire instead
  • Vire's C interop layer — LIB types, struct, cast/retrieve, and callbacks
  • How to use Xeon, the build/package manager, to compile, run, and ship programs

How this book is structured

Chapters build on each other within each language. Read the Rubidium chapters first if you're new — Vire deliberately reuses almost all of Rubidium's core syntax, so its chapters only cover what's different. Every chapter contains working code examples you can copy and run immediately with Xeon.

💡

File extensions: Rubidium source files use .rub; Vire source files use .vire. Both are built with the same tool — Xeon. You'll set it up in the next chapter.

Chapter 01

Getting Started

Install Xeon, create your first project, and run your first Rubidium program.

Installing Xeon

Xeon is the official project, build, and package manager for Rubidium. You use it to initialise projects, run static checks, compile code, and run programs. Install it by cloning the repository and running the installer for your platform.

Linux / macOS
git clone https://github.com/TomDexterYoutube/Xeon-Rubidium
cd Xeon-Rubidium
./install.sh
Windows (PowerShell)
git clone https://github.com/TomDexterYoutube/Xeon-Rubidium
cd Xeon-Rubidium
install.ps1

Creating a project

Make a new folder and run xeon init inside it. Xeon creates the src/ directory and a main.rub entry point for you.

terminal
mkdir hello-world
cd hello-world
xeon init

Your first program

Open src/main.rub and write the following:

src/main.rub Rubidium 
fn main() {
    print("Hello, Rubidium!")
}

Now compile and run it:

terminal
xeon run

You should see: Hello, Rubidium!

The execution model

Rubidium programs run in two phases — understanding this now saves confusion later.

  • Phase 1 — Top level: Everything written outside a function runs first, top to bottom. Variables are created, functions and classes are defined (but not called).
  • Phase 2 — Main: After the top level finishes, the compiler automatically calls fn main().
src/main.rub Rubidium 
print("Phase 1 — this runs first")

fn main() {
    print("Phase 2 — this runs second")
}

The Xeon command set

CommandWhat it does
xeon initScaffolds src/ and main.rub
xeon checkRuns the static analyzer only, no compile
xeon buildStatic checks, then debugger, then compiles to native code (-s for a shared library, --no-debug to skip the debugger)
xeon runBuilds, then immediately executes the binary
xeon pkgInstalls/removes/upgrades packages from the Xeon registry
xeon updatePulls the latest compiler, debugger, and CLI itself
💡

Tip: A .vire file referenced by an FFI(...) call anywhere in your project is compiled automatically as part of xeon build — you never invoke Vire's compiler directly.

Build flags, in depth

xeon build and xeon run both accept the same flags. Combine -s with --native to cross-tune a shared library for a specific CPU family, for example.

FlagEffect
-sCompile as a shared library (.so/.dll/.dylib), no entry point — exported fns become callable via FFI. Not valid with run, since there's nothing to execute.
--no-debugSkip the debugger pass during build/run — faster, but you lose its pre-flight error checking.
--native currentTune for this exact machine's CPU (-march=native). Fastest, but the binary won't run on other machines.
--native amd64 / amd32Generic 64-bit or 32-bit x86 (Intel or AMD) — no per-CPU tuning, runs anywhere in that family.
--native arm64 / arm32Generic 64-bit (aarch64) or 32-bit (armhf) ARM.

What the debugger actually does

The debugger isn't just static analysis — it interprets your program for real before the compiler even starts, as one more error-catching pass. For a program with side effects (opening windows, printing, reading input), that means its output runs once during the debug pass and then again for real once the compiled binary executes. Xeon brackets the debugger's own output clearly so it's never confused with the real run:

terminal
$ xeon run

   for errors; anything it prints below is from THAT run, not
   from the real compiled program.
════════════════════════════════════════════════════════
Hello, Rubidium!
════════════════════════════════════════════════════════
🔍 END DEBUGGER OUTPUT
════════════════════════════════════════════════════════

▶ RUNNING build/hello-world — this is the real compiled program.
════════════════════════════════════════════════════════

════════════════════════════════════════════════════════

Pass --no-debug once you trust the code and just want a faster build/run loop.

Chapter 02

Variables & Types

How to declare variables, annotate types, and work with Rubidium's type system.

Declaring variables

Use let to declare a variable. The type annotation goes after the variable name, separated by a colon. Type annotations are optional — Rubidium can infer the type from the value.

variables.rubRubidium
# With type annotation (colon before the type)
let name:  str  = "Rubidium"
let score: i32  = 100
let pi:    f64  = 3.14159
let alive: bool = True

# Without annotation — type is inferred
let x = 42         # inferred as i32
let msg = "hello"  # inferred as str

Mutable variables

By default, variables cannot be reassigned. Add mut if you need to change the value later. Trying to reassign a non-mut variable is a compile error. Re-declaring a name with let drops the old variable and creates a brand new one in its place.

mut.rubRubidium
let mut count: i32 = 0
count = count + 1    # OK — count is mut

let name: str = "Alice"
name = "Bob"          # ERROR: name is not mutable

let name = "Carol"   # fine — drops the old 'name', creates a fresh one

All available types

TypeDescriptionExample
i32 … i2048Signed integers — i32, i64, i128, i256, i512, i1024, i2048let x: i32 = 100
f32 / f64 / f128Floating pointlet x: f64 = 3.14
str / str+Text — str+ is triple-quoted & multi-linelet s: str = "hi"
boolTrue or Falselet b: bool = True
AnyHolds a value of any typelet x: Any = 5
SYA string usable as code (variable/function names)let n: SY = 'thing'
NullValid for any type — emptylet x: i32 = Null

The four collection types — list, index, dict, and dict+ — get their own chapters next.

Null

Null is a valid value for every type. It means the variable exists but currently holds no data, and it behaves like negative infinity when compared.

null.rubRubidium
let x: i32 = Null

Null < 0          # True
Null < -999999   # True
Null == Null    # True

Type casting

Use the as keyword to cast between types.

casting.rubRubidium
let y:     i32 = 5
let large: i64 = y as i64
let f:     f64 = 100 as f64

Mathematics

Standard operators, plus two worth calling out: ** is power (N ** X raises N to the Xth), and */ is root (N */ X takes the Nth root of X).

math.rubRubidium
let a = 10 + 5     # 15  — addition
let b = 10 - 5     # 5   — subtraction
let c = 10 * 5     # 50  — multiplication
let d = 10 / 5     # 2   — division
let e = 2 ** 3    # 8   — power (2 to the 3rd)
let f = 2 */ 16   # 4   — root (2nd root of 16)

# Standard BODMAS precedence applies
let g = 1 + 2 * 3    # 7
let h = (1 + 2) * 3  # 9

Typed math blocks

A parenthesised expression can carry a result type with : TYPE right after the closing bracket — the whole expression computes at that precision, not just the final value.

typed-math.rubRubidium
let r = (10 / 3): f64   # 3.3333... — division done AS f64
let d = (10 / 3): i32   # 3 — integer block keeps integer arithmetic
let n = ((10 / 3): f64 + 1): f128   # blocks can nest

Comparison & logic

logic.rubRubidium
# Comparison — returns bool
let check: bool = 10 > 5    # True
# == != > < >= <=

# Logic — and, or, not
let result: bool = True and not False   # True

Integer overflow doesn't wrap

When an operation would exceed a type's maximum or minimum value, the result stays clamped at that max/min — it never silently wraps around the way C's signed overflow can. A non-fatal runtime error is still raised to flag it, but unlike other runtime errors, it does not require a try/error block — the program keeps running with the clamped value.

⚠️

Overflow errors are reported once per operation, and the clamped result is stored before execution continues — so a loop that keeps overflowing the same variable will keep printing warnings, not crash.

Where variables are visible

A few scope rules apply consistently everywhere in Rubidium, worth internalizing early:

  • Symbols resolve from the nearest scope outward — a local always wins over a global with the same name (shadowing).
  • While a local shadow exists, there is no syntax to reach the hidden global — it becomes accessible again only once the local is dropped.
  • Variables, functions, classes, and namespaces must all have unique names within their scope; duplicate definitions are compile errors.
  • Assigning to a name that was never declared with let is a compile error — you can't create a variable by accident.

Chapter 03

Strings, SY & str+

Working with text — methods, interpolation, code-as-string, and multi-line strings.

Basic strings

Strings are declared with double quotes and the str type, and are zero-indexed.

strings.rubRubidium
let text: str = "Hello World"
print(text)   # Hello World

let empty = ""   # empty string is valid

String interpolation

Use i"" (an interpolated string) to embed variable values directly inside text. Wrap the variable in {}. Plain + concatenation also works between strings and other values.

interpolation.rubRubidium
let name:  str = "Alice"
let score: i32 = 42

print(i"Hello, {name}!")         # Hello, Alice!
print("Count: " + score)       # Count: 42

String methods

string-methods.rubRubidium
let mut text = "Hello"

print(text.char(0))         # H — character at index
text.set(0, "J")          # Jello — replace one character
text.insert(5, "!")      # Jello! — insert before an index
text.replace("l", "_")     # replace every match
print(text.slice())        # list of characters
print(text.len())          # character count

User input

input() reads a line of text from the user and returns it as a str.

input.rubRubidium
let user: str = input("Enter your name: ")
print(i"Hello, {user}!")

SY — code as a string

SY holds a string that can be used as code — a variable or function name that's built at write-time. Wrap it in () when used, and 'single quotes' when it's made.

sy.rubRubidium
let function_name: SY = 'New function'

fn (function_name)() {
    print("I'm a new Function")
}

str+ — multi-line strings

str+ is the same as str but uses triple double-quotes and can span multiple lines.

strplus.rubRubidium
let big: str+ = """
Hello
I'm a big string!
"""

Program output & control

A handful of built-ins round out console I/O and process control — none require a use import.

control.rubRubidium
# println() overwrites the current console line instead of adding a new one
println("Loading...")
println("Done!")
# The console shows only: Done!

# clear() wipes the WHOLE terminal screen, not just the current line
print("Hello!")
clear()
print("You won't see 'Hello!' anymore")

# exit([code]) terminates immediately from anywhere — no cleanup, no drop()s run
fn check(n: i32) {
    if n < 0 {
        print("negative — stopping")
        exit(1)
    }
}

# arg() returns the program's command-line arguments as one joined string
let cmdline: str = arg()
if cmdline.has("--help") {
    print("usage: my_program [--mode speed]")
    exit(0)
}

Both exit() and arg() are callable from anywhere in the program, not just main() — useful for an early argument check before any real setup runs.

Chapter 04

Collections — List

An ordered, zero-indexed sequence that can hold mixed types.

Creating a list

Use square brackets. Lists require mut to be modified.

list.rubRubidium
let mut items: list = ["hello", 2.5, True]

Accessing items

Access by index using call syntax — items(0), never items[0].

list-access.rubRubidium
print(items(0))   # hello
print(items(1))   # 2.5
print(items(2))   # True

Mutating items

Use .set() to change an item in place.

list-mutate.rubRubidium
items(0).set("changed")
print(items(0))   # changed

Appending & removing

Use .add() on the list itself (empty parentheses) to append. .drop() on an element removes it and shifts the structure — it does not replace it with Null.

list-add.rubRubidium
items().add("new item")
items(1).drop()   # removes index 1, shifts everything after it left

List utilities

.combine() joins every value in a list of strings together.

list-utils.rubRubidium
let words = ["Hello", " ", "World"]
print(words.combine())   # Hello World

Deep copy rule

Assigning a list to a new variable creates a full deep copy. Modifying the copy does not affect the original.

deep-copy.rubRubidium
let mut a: list = [1, 2, 3]
let mut b = a

b(0).set(999)

print(a)   # [1, 2, 3]  — unchanged
print(b)   # [999, 2, 3]

Iterating over a list

Use a for loop. The loop variable is automatically freed when the loop ends.

list-iter.rubRubidium
let mut nums: list = [10, 20, 30]

for item in nums {
    print(item)
}
# prints 10, 20, 30

Forcing an element type

A list can pin down the type every element must be, with a second colon — useful when the list needs to cross an FFI boundary later, or you just want the compiler catching mismatches early.

typed-list.rubRubidium
let x: list: i32 = [0, 10, 32]

How .add() treats a lone Null

.set() and .add() always destroy a Null they replace — it's never preserved. Normally .add() appends and keeps every existing value. The one exception: a collection holding only a single Null treats .add() as replacing that Null instead of appending next to it.

null-add.rubRubidium
[Null].add(5)         # [5]        — the lone Null is replaced
[1, Null].add(5)   # [1, Null, 5] — Null isn't alone, so it's kept
💡

Collection equality compares contents recursively, not identity — two lists (or dicts, or dict+s) built separately are equal if every element matches, Nulls included.

Chapter 05

Collections — Index

A flat key→value map. Keys can be any type — values must be a single scalar.

💡

Index vs Dict: An index maps one key to one scalar value. A dict maps one key to a collection of values. They look similar but behave differently — see the next chapter for dict.

Creating an index

Uses square brackets with a colon : separating keys from values.

index.rubRubidium
let mut my_index: index = [
    "name":  "Rubidium",
    1:       "one",
    2.5:     "float key"
]

Accessing values

Access by key using call syntax.

index-access.rubRubidium
print(my_index("name"))   # Rubidium
print(my_index(1))         # one

Mutating a value

index-mutate.rubRubidium
my_index("name").set("updated")
print(my_index("name"))   # updated

Adding a new key

Use .add(key, value). This errors if the key already exists.

index-add.rubRubidium
my_index().add("new_key", 99)
⚠️

Note: Calling .add() with a key that already exists produces a runtime error. Use .set() to update an existing key instead. Iterating an index yields its keys, in insertion order.

Chapter 06

Collections — Dict & Dict+

A key→collection map, and its unlimited-depth nesting sibling.

Creating a dict

Uses curly braces with = separating keys from their value lists.

dict.rubRubidium
let mut my_dict: dict = {
    "scores" = [10, 20, 30],
    "names"  = ["alice", "bob"]
}

Accessing values

Access with dict(key, index) — you need both the key and the position within that key's collection.

dict-access.rubRubidium
print(my_dict("scores", 0))   # 10
print(my_dict("scores", 1))   # 20
print(my_dict("names",  0))   # alice

Mutating & adding values

dict-mutate.rubRubidium
my_dict("scores", 1).set(999)     # mutate
my_dict("scores").add(40)        # append to a key's collection
my_dict().add("new_key")         # new top-level key, starts as Null

Iterating over a dict

A for loop over a dict yields keys, not values. Use the key to access values.

dict-iter.rubRubidium
for key in my_dict {
    print(key)
    print(my_dict(key, 0))
}

Dict+ — unlimited nesting

dict+ is like dict, but a key's value can be either a list (a leaf, same as normal dict) or another dict+ — nested to any depth. Chain keys to drill down through each level.

dictplus.rubRubidium
let mut my_dictplus: dict+ = {
    1 = {
        "test" = [1, 2, 3, 4]
    }
}

print(my_dictplus(1, "test"))          # [1, 2, 3, 4]
print(my_dictplus(1, "test", 0))       # 1

my_dictplus(1, "test").add("ten")
my_dictplus(1).add("deeper", { "layer2" = [8, 9] })
my_dictplus().add(2)   # new top-level key, starts as an empty dict+

Collection comparison

TypeSyntaxAccessUse when…
list[a, b, c]list(0)Ordered sequence of items
index["k": v]index("k")One key → one scalar value
dict{"k" = [...]}dict("k", 0)One key → many values
dict+{k = {...}}dictplus(k1, k2, ...)Unlimited nested keys

Chapter 07

Control Flow

Branching with if/else, looping with while and for.

if / else if / else

conditionals.rubRubidium
let x = 7

if x == 7 {
    print("lucky seven")
} else if x > 10 {
    print("big number")
} else {
    print("something else")
}

while loop

while.rubRubidium
let mut count = 0

while count < 5 {
    print(count)
    count = count + 1
}

for loop with range

range(start, end) — end is exclusive. The loop variable is automatically freed at the end of the block.

for-range.rubRubidium
for i in range(1, 10) {
    if i == 5 {
        break
    }
    print(i)
}
# prints 1 2 3 4

break & continue

break-continue.rubRubidium
for i in range(1, 10) {
    if i == 5 { continue }   # skip this iteration
    print(i)
}
💡

Loop variables are auto-freed. The loop variable is automatically dropped at the end of the loop block — you don't need to call .drop() on it. Lists yield values, indexes/dicts/dict+ yield keys, and files yield lines.

Chapter 08

Functions

Defining reusable, isolated pieces of logic — with defaults and named arguments.

Basic function

functions.rubRubidium
fn greet() {
    print("Hello!")
}

greet()

Parameters and return types

Parameter types and the return type use the same colon annotation as variables. The return type goes after ->, and is optional — a function with none returns nothing.

params.rubRubidium
fn add(a: i32, b: i32) -> i32 {
    return a + b
}

let result: i32 = add(10, 32)
print(result)   # 42

Default parameter values

A parameter can declare a default with = value right after its type. Parameters without a default must all come before ones that have one.

defaults.rubRubidium
fn add(a: i32, b: i32 = 5) -> i32 {
    return a + b
}

add(7)      # 12 — b uses its default
add(7, 3)   # 10 — b explicit

Named arguments

A call can bind arguments by parameter name, in any order. Positional arguments must all come before named ones.

named-args.rubRubidium
add(7, b = 3)          # OK — positional then named
add(a = 7, b = 3)      # OK — all named, any order
# add(a = 7, 3)  # ERROR: positional argument follows a named one

Naming a parameter that doesn't exist, naming the same parameter twice, or leaving a no-default parameter unfilled are all compile errors — caught before the program ever runs:

named-arg-errors.rubRubidium
# add(c = 1)         # ERROR: no parameter named 'c'
# add(1, a = 2)      # ERROR: multiple values for parameter 'a'
fn needs_two(a: i32, b: i32) {}
# needs_two(a = 1)   # ERROR: missing required argument 'b'
💡

No overloading. Function names must be unique within their scope — Rubidium has no concept of choosing between multiple functions with the same name by argument type or count. A duplicate definition is a compile error. Defaults and named arguments work identically for class methods (see the next chapter).

Chapter 09

Memory, Local & Link

Rubidium has no garbage collector. You manage memory explicitly with .drop() — and opt out of copying with local and link.

The global pool

All variables — unless declared local — live in a shared global pool. Think of it as a whiteboard everyone can see and write on. Memory on this whiteboard is never freed automatically.

Freeing memory with .drop()

drop.rubRubidium
let val = 42
val.drop()
# val no longer exists after this point

let mut items: list = [1, 2, 3]
items.drop()
# All nested data inside items is freed too

local — opting out of the global pool

let local keeps a variable off the global pool entirely — it exists only for its current block/function/loop and is dropped automatically when that scope ends.

local.rubRubidium
while True {
    let local num = 10
    break
}
# num is already gone — this holds true for loops, functions,
# while loops, and if blocks

link — sharing instead of copying

Every assignment is a deep copy by default. link is the one opt-in exception — it shares a variable instead of copying it, useful for passing a large local value into another function without paying for the copy.

link.rubRubidium
fn stuff(val: Any) -> Any {
    val.add(7)
}

fn main() {
    let local large_list: list = ["Lots of Data"]
    stuff(link large_list)   # shared, no deep copy — both sides can edit it
}

If a later changes, a linked b changes with it — but if b is reassigned without a, they unlink and b becomes its own independent variable.

Automatic cleanup

Two cases clean up memory for you automatically — no .drop() needed:

  • Loop variables — freed at the end of each iteration.
  • open() file blocks — the file handle closes and frees when the block exits.
🔴

No GC — memory won't free itself. If you create variables in a long-running loop and never drop them, your program's memory usage will grow. Get in the habit of calling .drop() when you're done with a value.

Chapter 10

Classes

Self-contained object templates. No self keyword — class variables are accessed directly.

Defining a class

classes.rubRubidium
class player() {

    let mut health: i32  = 100
    let mut name:   str  = "unnamed"
    let mut scores: list = [0, 0, 0]

    fn greet() {
        print(i"Hi, I am {name}")
    }

    fn take_damage(amount: i32) {
        health = health - amount
    }
}

Creating an instance

instance.rubRubidium
let mut p = player()

print(p.health)   # 100

Mutating fields

For non-collection fields, use = directly. For collection fields, use .set()/.add(). The instance must be declared with mut, and only fields the class itself marked mut can change.

mutating.rubRubidium
# Non-collection field
p.health = 80
p.name   = "Alice"

# Collection field — use .set() from outside the class
p.scores(0).set(99)
p.scores().add(50)

# Call a method
p.greet()
p.take_damage(10)

Inside methods — no instance prefix

Inside a class method, fields (including collections) are accessed directly by name — no self. or instance prefix needed.

inside-method.rubRubidium
fn take_damage(amount: i32) {
    health = health - amount   # direct field access, no self
}

Immutable fields & deep copy

Fields declared without mut can never be changed from outside the class. Class instances follow the same deep-copy rule as everything else — but store their fields outside the global pool.

locked.rubRubidium
class locked() {
    let value: i32 = 42   # not mut — cannot be changed
}

let mut obj = locked()
obj.value = 99   # ERROR: value is not declared mut

let mut a = player()
let mut b = a       # full deep copy
b.health = 10
print(a.health)   # 100 — untouched

Chapter 11

Error Handling

Catch runtime errors gracefully with try / error, and trigger your own with raise.

try / error

Wrap risky code in a try block. If anything inside it fails at runtime, execution jumps to the error block. The special variable error holds the error message as a str+.

try.rubRubidium
try {
    let bad: i32 = 10 / 0
} error {
    print("Error: " + error)
}

raise — triggering your own errors

Inside a try block (directly, or inside a function called from within it), a raise is caught by the nearest enclosing handler. Outside of any try, raise halts the program.

raise.rubRubidium
fn check(n: i32) {
    if n < 0 {
        raise "n must not be negative"
    }
}

try {
    check(-1)
} error {
    print("Error: " + error)   # Error: n must not be negative
}
💡

Always wrap file I/O in try/error — files can fail to open for many reasons (missing, wrong permissions, network drives). It's good practice to handle those cases explicitly.

Compile-time vs. runtime errors

Rubidium catches as much as it can before your program ever runs. Only try/error deals with runtime errors — a compile error stops the build outright, with nothing to catch.

Compile errors (build fails)Runtime errors (catchable with try/error)
Unknown variable, function, class, or namespaceDivide by zero
Type mismatchInvalid index / missing collection key
Mutability violation (editing a non-mut value)Accessing dropped memory
Duplicate symbol definitionInvalid file operations
Invalid assignment targetInvalid FFI calls

One deliberate exception on the runtime side: integer overflow is a runtime condition that does not require a try/error block — it just clamps and keeps going.

Chapter 12

Files

Reading, writing, and managing files on disk.

Opening a file

Chapter 18 · Vire

What Is FFI, Really?

Starting from zero — assuming you know only Rubidium, and have never touched C, pointers, or memory addresses.

Why Rubidium can just... call Rubidium

Think about what happens when your main.rub calls a function from an imported file, or from an FFI("lib.so") library built with xeon build -s. It just works — you pass a list, a dict+, a class instance, anything, and it arrives on the other side intact. That's not an accident. Every Rubidium binary is produced by the exact same compiler, which means every Rubidium binary agrees, byte for byte, on how a list is laid out in memory, how a class instance is laid out, how the global pool tracks what's alive. Calling from one Rubidium binary into another is like two people who grew up speaking the exact same dialect — no translation needed.

Why Rubidium can't just call C the same way

A C library (OpenGL, GLFW, the C standard library, ...) was not built by the Rubidium compiler. It was built by gcc or clang, which has its own, completely different idea of how data should be laid out in memory — no global pool, no Null, no deep-copy semantics, no list/dict concept at all. It only knows about raw bytes at raw memory addresses, arranged exactly the way the C compiler decided decades ago. Handing a Rubidium list straight to a C function would be like handing someone a sentence in a language they've never heard — the bytes would be there, but nothing about their meaning or shape would carry over.

Vire (.vire files) exists to be that translator. It's Rubidium's own sibling language — same core syntax, same let/mut/if/for/class/thread you already know — but it additionally understands C's rules for how data is laid out, so it can sit exactly on the boundary between "Rubidium's world" and "C's world" and translate carefully in both directions.

🔌

The one-sentence version: use Rubidium's own FFI(...) when the other side is another Rubidium-compiled library (same dialect, no translation needed — see the previous chapter). Reach for Vire specifically when the other side is a genuine foreign C library, because that's the only place a translator is actually required.

Vire's syntax is (almost) Rubidium's syntax

This is the reassuring part: you are not learning a new language from scratch. Variables, mutability, the deep-copy rule, link, collections, functions (defaults + named args), try/error, classes, and threading all work exactly the way you already learned them in the Rubidium chapters. This chapter and the ones after it only cover what's genuinely new: the handful of extra concepts needed to describe C's world precisely enough to talk to it safely.

One behavioral difference: no top-level execution

In Rubidium, code written outside fn main() runs immediately, top to bottom, before main() is called (Chapter 01). A .vire file has no such phase — nothing runs until a function is explicitly called from somewhere else. The only exception is the one-time work of loading an FFI library itself.

example.vireVire
# nothing here runs on its own — only when a fn is called
fn add(a: i32, b: i32) -> i32 {
    return a + b
}

This makes sense once you see what a .vire file actually becomes (next section): it has no "start here" the way main() gives Rubidium one — it's a bag of callable bindings and helper functions, waiting to be used by whoever loads it.

A .vire file is always a shared library

Recall from the Xeon chapter that xeon build -s compiles Rubidium code into a shared library instead of a runnable program — no entry point, just exported functions other code can call into. A .vire file is always built that way; there's no non--s mode for it, because a translator layer was never meant to be run on its own — it exists purely to be loaded and called into, either from your Rubidium program or from the C library on the other side.

In practice you never invoke Vire's compiler by hand at all: Xeon detects any .vire file referenced by an FFI(...) call anywhere in your project and compiles it automatically as part of xeon build, before your main program.

Chapter 19 · Vire

Pointers

The one thing Rubidium never shows you, and why C can't live without it. Read this chapter slowly — everything else in Vire builds on it.

Rubidium hid something from you, on purpose

Go back to Chapter 09. Rubidium's whole memory model is "a shared global pool — a whiteboard everyone can read and write." Notice what's missing from that description: where, physically, in the computer's RAM, a variable actually lives. You've never had to know, or care. You write let x = 42 and later print(x), and Rubidium finds it for you every time. That's a deliberate design choice — memory addresses are exactly the kind of bookkeeping detail Rubidium's philosophy (Chapter 00) wants to keep invisible.

C was designed with the opposite philosophy: the address of a piece of data is a first-class thing you constantly see and work with. To talk to a C library at all, Vire has to expose that concept — carefully, in one place, rather than scattering it everywhere.

What a memory address actually is

Picture your computer's RAM as an enormous single row of numbered mail slots — slot 0, slot 1, slot 2, all the way up into the billions, each one holding a byte. A memory address is just a number: which slot. When a C function stores a value (say, an image's width), it stores it in some particular slot — slot number 4,398,046,511,104, or whatever it happened to land on. A pointer is nothing more than a variable whose value is one of these slot numbers — it "points at" that slot.

That's it. That's the entire concept. In C, void* means "a pointer to some slot, but I'm not telling you what type of data lives there." char* means "a pointer to a slot holding character/text data." A pointer is never the data itself — it's the street address of the data, which is why "dereferencing" (reading through) a pointer means "go to that slot number and read what's actually stored there."

🔌

Why Rubidium never needed this: every Rubidium value already carries its own "where do I live and what am I" bookkeeping automatically, invisibly, as part of the global pool. A pointer is what's left over once you take all of that automatic bookkeeping away and are left with a bare number.

Why pointers exist at all — the two jobs they do

A raw address is only useful because of two things you can do with it. First: hand it to someone else instead of copying the data. Rubidium's link (Chapter 09) achieves the same effect — sharing instead of copying — but does it invisibly, through the global pool. C achieves it by literally passing the number of the slot around; whoever holds that number can reach the exact same data, no copy involved. Second: describe an out-parameter — a C function that "returns" a value by writing it into a slot you chose ahead of time and told it about, rather than handing a value back directly. Both patterns show up constantly once you start reading real C library headers.

Pointer-to-pointer — one more level of indirection

Once "a pointer is a number naming a slot" clicks, this follows naturally: nothing stops a slot from holding another slot's number. A pointer-to-pointer (void**/char**) is exactly that — the address of a slot which itself contains an address. Some C APIs hand these back, or want them, when a function needs to write out an address as its result rather than an ordinary value.

double-ptr.vireVire
fn glfw get_double_ptr() -> void** as get_double_ptr
fn glfw read_through_double_ptr(pp: void**) -> int as read_through

let dp: void** = get_double_ptr()
let val = read_through_double_ptr(dp)

Today this only covers storing and relaying a void**/char** that already came from C — there's no way yet to take "the address of" an existing Vire variable to manufacture a new out-parameter yourself (C's &my_var-style calls).

LIB Types

The full set of C's raw memory-shape types, and why they exist as a separate list from Rubidium's own types.

Why C needs exact byte widths

Because C works directly with raw slots of memory (previous chapter), it has to know exactly how many slots a value occupies — 1 byte, 4 bytes, 8 bytes — with no wiggle room, or it would read a neighboring value's bytes by mistake. Rubidium's i32 is a promise about the range of numbers it can hold; C's int is a promise about the exact number of memory slots it occupies (conventionally 4 — but this can vary by platform, which is exactly why the fixed-width types like int32_t exist: "I mean 4 bytes, no matter what platform this runs on"). This is the entire reason LIB types exist as a separate list from Rubidium types — they're not offering new kinds of numbers, they're pinning down an exact memory shape that C's compiler already agreed to, decades ago, that Vire now has to match precisely.

The full LIB type list

Alongside every normal Rubidium type, Vire adds the full set of C primitive types for describing a foreign function's real signature.

CategoryExamples
Integerschar, int, long, long long, unsigned variants
Fixed-widthint8_t … int128_t, uint8_t … uint128_t
Floatsfloat, double, long double
Pointersvoid* (address of unknown-type data), char* (address of text), ptr (a resolved, callable address — see Chapter 23)
Othersize_t, ptrdiff_t, intptr_t, uintptr_t

Almost every one of these is either an integer width, a float width, or a pointer (a number naming a slot — the previous chapter). There's no fundamentally new concept here, just C's much finer-grained vocabulary for "exactly how many bytes, exactly what shape."

When no conversion is needed at all

A few LIB types happen to occupy exactly the same memory shape as an existing Rubidium type — same byte width, same interpretation of those bytes.

struct

Several values sitting at consecutive memory addresses, back to back — and why it looks nothing like a Rubidium class underneath.

struct vs. class — the honest comparison

You already know class. When you write class Player() { let mut health: i32 = 100 } and then player(), Rubidium quietly does a huge amount of invisible work: it allocates memory, tags it as "this is a Player," wires up deep-copy semantics, hooks it into whatever memory management the compiler decided on — all of it automatic, all of it hidden, precisely because every Rubidium binary was built by the same compiler and agrees on the rules.

C has none of that machinery. A C "struct" is nothing more than: starting at some address (previous-previous chapter), read these fields, in this exact order, each occupying this exact number of bytes (previous chapter). There's no tag anywhere in memory saying "this is a GLFWvidmode" — the C compiler just knows, from your source code, to read 4 bytes as width, then the next 4 as height, and so on. If Vire's struct declaration doesn't list the fields in the exact same order, with the exact same byte widths, as the real C struct, it will silently read the wrong bytes as the wrong field — no compiler on either side can catch that mistake, because both sides only ever see raw bytes at an address.

class (Rubidium)struct (Vire)
What it isA Rubidium object with hidden bookkeepingRaw bytes at an address, nothing more
MethodsYes, defined inside the classNever — just data
mutRequired to modify fieldsIrrelevant — every field is always read/write
Type tag in memoryYes, invisibly, by the compilerNone at all — you must know the shape by hand
Field orderDoesn't matter to correctnessMust match the real C struct exactly

Declaring one

struct is you, by hand, telling Vire "here is the exact layout the C side already agreed to" — a name and a LIB type per field, in declaration order, matching the real C struct's declaration order exactly.

struct.vireVire
struct Point {
    x: int
    y: int
}

struct Circle {
    position: Point      # embedded — bytes sit inline
    radius: int
}

let mut c = Circle()
c.position.x = 5
print(c.position.x)   # 5 — chained field access, any depth

Reading Circle as raw memory slots: [position.x: 4 bytes][position.y: 4 bytes][radius: 4 bytes] — twelve consecutive bytes, back to back, nothing in between. That's the entire "layout" a struct describes.

Two ways to get an instance

Circle() allocates a fresh block of zeroed memory of exactly the right size — same call syntax as a class, but there's no hidden object behind it, just those twelve raw bytes. Or, since a C function often hands you back the address of a struct it already built (a pointer — Chapter 19), you can type that address as the struct type instead — a zero-copy view straight over that same memory, no allocation, no copy, just a different lens on the same slots.

view.vireVire
let glfw = FFI("libglfw.so")
fn glfw glfwGetVideoMode(monitor: void*) -> void* as get_video_mode

let ptr = get_video_mode(primary_monitor)
let live_mode: GLFWvidmode = ptr   # a view, no allocation or copy
print(live_mode.width)              # reads directly out of GLFW's own memory

An owned struct variable already is its address, so it binds straight into a void* parameter with no extra syntax. A field typed Point* (trailing *) means a pointer to a separate struct instead of an embedded one.

Fixed-size array fields

type[N] on a field declares a fixed-length row built into the struct itself (C's float m[16]) — indexed like any collection, but always exactly N elements.

matrix.vireVire
struct Matrix4 {
    m: float[16]
}

let mut mat = Matrix4()
mat.m(0).set(1.0)
let first = mat.m(0)   # 1.0

There's no whole-array read/write — mat.m alone (no index) is a compile error, and it's not a growable Rubidium list either. It's always exactly N elements, laid out exactly the way the matching C struct is.

Passing or returning a struct by value

The void* form sends a struct's address — most C APIs that hand you a struct work that way. Some C functions instead want the actual bytes copied straight into or out of the call — a bare struct name in a binding's signature (no trailing *) means exactly that.

by-value.vireVire
fn glfw glfwGetWindowSize(w: void*) -> Size as get_window_size
fn glfw glfwResizeWindow(w: void*, s: Size) as resize_window

let sz = get_window_size(win)      # sz.width / sz.height read normally
resize_window(win, sz)             # sz's bytes are copied straight in

This follows the real x86-64 C calling convention automatically: small structs (16 bytes or less) pack into 1–2 registers, bigger ones cross via a hidden pointer — no annotation needed either way. It's only relevant when the other side of FFI(...) is a genuine foreign C library; a Vire function taking/returning a bare struct type between two Vire functions is just Vire calling Vire, no C convention involved.

Conversion

Moving values explicitly between Rubidium types and LIB types.

Why this needs to be explicit at all

In plain Rubidium, as converts between types silently and automatically wherever it's safe to (Chapter 02) — 5 as f64 just works, because both sides are still "Rubidium's world," with the same global-pool bookkeeping underneath. The moment a value needs to cross into "C's world" (the previous chapter), that bookkeeping doesn't exist anymore on the other side — there's no global pool over there, just raw bytes at an address. Vire refuses to let that crossing happen silently: cast/retrieve are the one explicit, visible checkpoint where a value stops being a Rubidium value and starts being (or stops being) a raw C-shaped one.

cast.X / retrieve.X

cast.X(value) and retrieve.X(value) are the same underlying operation — X is always the target type. The name just reads naturally for the direction: cast heading out to a LIB type, retrieve heading back into a Rubidium type.

conversion.vireVire
let a: i64 = 5000000000
let b = cast.int(a)        # narrows i64 -> int (i32), clamps to range

let s: str = "hello"
let cs = cast.cstr(s)       # str -> char* — same representation, no reshape
let back: str = retrieve.str(cs)

Buffers — flattening a list into a C array

Rubidium's list has no raw C layout. cast.list(list, elem_type) flattens one into a contiguous C array (e.g. for glBufferData); retrieve.list(ptr, elem_type, count) reads one back — the same trick reads an out-parameter a C function wrote into.

buffers.vireVire
let verts: list: f32 = [0.0, 1.0, 0.0]
let buf = cast.list(verts, f32)

let mut placeholder: list: i32 = [0, 0, 0]
let out_buf = cast.list(placeholder, i32)
# some_c_fn(out_buf, 3)  -- writes 3 ints into out_buf
let results: list = retrieve.list(out_buf, i32, 3)
🔌

Unsigned values retrieve wider. Reading an unsigned LIB value back always lands on a wider Rubidium int than that width would normally give — e.g. retrieve.uint32 gives you an i64, not an i32. Rubidium has no unsigned concept, so a huge unsigned C value can never come back misread as negative.

FFI Bindings

Binding against a genuine foreign C library — including runtime-resolved addresses and variadic functions.

What a "binding" actually declares

Remember: a shared library (.so/.dll) on disk is, underneath, just a block of compiled machine code, plus a table of names ("symbols") mapping each exported function to the address where its code starts. FFI("libglfw.so") loads that block into your program's memory and gives you a handle onto it. A binding — fn glfw glfwInit() -> int as glfw_init — tells Vire three things: look up this exact symbol name in that library, here is what its parameters and return value actually are, byte-for-byte, and let me call it under this friendlier local name. Nothing is verified for you — if you describe the wrong parameter types, Vire will still make the call, reading/writing the wrong number of bytes, because from the outside a foreign function call is just "jump to this address, treating the stack/registers the way I was told to."

Basic bindings

A binding's parameter/return types can freely mix Rubidium and LIB types depending on what's really on the other side of FFI("...").

glfw.vireVire
let glfw = FFI("libglfw.so")

fn glfw glfwInit() -> int as glfw_init
fn glfw glfwCreateWindow(width: int, height: int, title: char*, monitor: void*, share: void*) -> void* as create_window
fn glfw glfwGetTime() -> double as get_time

fn main() {
    glfw_init()
    let win = create_window(800, 600, "Hello Vire", Null, Null)
    let t = get_time()
}
⚠️

dict/dict+/index can never cross an FFI boundary — not even to another Rubidium binary. list only crosses via the explicit buffer cast from the previous chapter.

Binding against a resolved address

The ordinary binding form above assumes the symbol table trick from the last section always works — you name a function, the loader looks it up. Some APIs (OpenGL past the oldest baseline functions) genuinely can't be looked up that way: the real function might live inside a graphics driver, chosen at runtime depending on the exact GPU installed, so there's no fixed symbol name to search for ahead of time. The fix mirrors exactly what you'd expect from "an address is just a number": ask a helper function, at runtime, "what address does glGenBuffers live at on this machine, right now" — it hands back a ptr — and then bind directly against that specific number instead of a name, with fn ptr <var>(...) instead of fn <lib> <symbol>(...).

resolved.vireVire
fn glfw glXGetProcAddress(name: char*) -> ptr as get_proc_address

let raw: ptr = get_proc_address("glGenBuffers")
fn ptr raw(n: int, buffers: void*) as gen_buffers

gen_buffers(1, out_buf)

Variadic functions

Some C functions (printf-style) take a flexible number of arguments — end a binding's parameter list with ... (must be last) to declare one.

variadic.vireVire
let libc = FFI("libc.so.6")
fn libc printf(fmt: char*, ...) as c_printf

c_printf(cast.cstr("%d + %d = %d\n"), 3, 4, 7)

There's no way to forward a variadic call through an intermediate Vire function — each call site's argument types have to be known to build the call. Call the binding directly. Each variadic argument is promoted the same way C itself does: a float widens to double, anything narrower than a plain int (bool, a byte) widens to i32 — matching what a real variadic function like printf expects to read.

Renaming & wrapping foreign functions

Just like Rubidium's own FFI, an ugly foreign symbol name can be exposed under a clean one with as, and wrapped in an ordinary Vire function.

rename.vireVire
let math_lib = FFI("libs/math.so")

fn math_lib rb_sqrt(x: f64) -> f64 as raw_sqrt

fn sqrt(value: f64) -> f64 {
    return math_lib.raw_sqrt(value)
}

Importing FFI wrappers across files

A file that only exists to hold bindings can be imported like any other Vire file — the importer never touches FFI(...) directly.

math_tools.vireVire
let native = FFI("libs/math.so")

fn native native_sin(x: f64) -> f64 as sin
fn native_sqrt(x: f64) -> f64 as sqrt
another_file.vireVire
import math_tools as mt

mt.sin(1.0)
mt.sqrt(25.0)

Callbacks

Handing a Vire function to a C library as an event handler.

Compiled functions live at addresses too

One more piece falls into place once you've internalized "an address is just a number pointing at some memory": your compiled function's code itself also sits somewhere in memory, at its own address, the same as any struct or piece of data. Every binding you've written so far has Vire doing the calling — you look up an address, jump to it, C runs, hands an answer back. A callback flips that around entirely: instead of you calling into C, you hand C the address of your own function's code, and C stores that number away to jump to itself, later, whenever it decides to — a keypress, a window resize, whenever. This is exactly why "hand off the function, no parentheses" (below) matters so much: parentheses call the function right now and hand C the result; no parentheses hands C the function's raw address to call itself.

fn callback

There's a wrinkle: an ordinary Vire function's compiled code assumes it's only ever entered by other Vire code, which quietly does setup on every call — memory bookkeeping, error-reporting plumbing — the same invisible machinery Chapter 18 mentioned every Rubidium-family binary relies on. C has no idea any of that setup needs to happen; if C jumped straight to a plain function's raw address, that setup would simply never run. fn callback builds a small wrapper in front of your function — one that does Vire's setup first, then calls your real code — and hands C the wrapper's address instead of your function's bare one. You never see the wrapper; you just write fn callback instead of fn, and it's built for you. It's a reserved word, same as local/open/file.

callback.vireVire
fn callback my_key_handler(key: int, action: int) {
    print(i"key pressed: {key}")
}

fn glfw glfwSetKeyCallback(window: void*, cb: void*) as set_key_callback
set_key_callback(win, my_key_handler)   # hand off the function itself, don't call it

Callback struct fields

The address doesn't have to live in a plain variable — some C structs have a field that holds a callable address (a "vtable"-style config struct). fn ptr accepts a struct field too, reading the address out of .field instead of a bare variable.

callback-field.vireVire
struct Handler {
    fn_ptr: ptr
    tag: int
}

let mut h = Handler()
h.fn_ptr = get_proc_address("some_c_function")

fn ptr h.fn_ptr(a: int, b: int) -> int as call_handler
call_handler(3, 4)
⚠️

Rules: use fn callback only for a function handed to a C library as an event handler — everything else stays a plain fn. Parameter/return types must match exactly what the C library will actually call your function with; the compiler cannot check this for you. Write the function name with no parentheses when handing it off — with parentheses, it's an ordinary call, right now, once.
