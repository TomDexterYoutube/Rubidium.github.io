Questions & Answers

Frequently Asked Questions

The "why" questions the spec implies but doesn't spell out.

Q.Why doesn't Rubidium have a garbage collector?
Because a GC hides when memory actually gets freed, and Rubidium's whole design philosophy is visible, predictable behavior over hidden machinery. Instead, memory lives in a shared global pool until you explicitly call .drop() — slower to write than a GC'd language sometimes, but you always know exactly what's alive.
Q.Why deep-copy everything instead of using references or an ownership system like Rust?
Same reasoning: ownership and borrow-checking are powerful, but they're also a second mental model you have to learn on top of the language itself. Rubidium picks one simple rule — assignment always copies — and gives you exactly one deliberate escape hatch, link, for when you actually want to share data.
Q.Why is Rubidium "global by default" instead of scoping variables to where they're declared, like most languages?
It's the same visibility-first tradeoff: a variable in the global pool can be inspected and reasoned about from anywhere, with no hidden scoping rules to track. If you want a variable to disappear at the end of a block, that's what local is for — it's opt-in rather than the default.
Q.What's actually the difference between dict and dict+?
dict is exactly two levels: a key, and a flat list of values under it. dict+ removes that limit — a key's value can be another whole dict+ block, nested as many times as you need. Reach for dict when your data is naturally flat, and dict+ for anything tree-shaped, like config files or nested categories.
Q.Why does Null behave like negative infinity instead of just being "nothing"?
Making Null comparable — always smaller than any real value — means you can sort, compare, and branch on it without special-casing "is this Null?" everywhere first. It's still exists-but-empty in meaning; it just also has a well-defined place in ordering.
Q.Is Rubidium compiled or interpreted?
Compiled — it targets native machine code via LLVM, built and run through the Xeon toolchain (xeon build / xeon run). See the benchmarks section for real, measured numbers against C and Rust rather than a marketing claim.
Q.Why no function overloading?
Consistent with the rest of the language: one name resolves to exactly one thing in a given scope, with no hidden resolution rules based on argument types. Two functions named add in the same scope is just a duplicate-symbol error, same as any other name collision.
Q.How do I contribute, report a bug, or ask something not covered here?
Open an issue or pull request on the GitHub repo — that's the source of truth for anything not covered in the book.
