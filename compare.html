Rubidium vs. Python vs. Rust vs. C vs. Java

The same eight tasks, written in all five languages, so you can see exactly where Rubidium's syntax sits — and where its memory model and error handling actually differ from the other four.

Variables & Mutation
Rubidium
let mut x: i32 = 10
x = 20
Python
x = 10
x = 20  # always reassignable
Rust
let mut x: i32 = 10;
x = 20;
C
int x = 10;
x = 20;
Java
int x = 10;
x = 20;  // final int locks it

Rubidium and Rust both require an explicit mut to allow reassignment. Java and C allow it by default unless marked final/const. Python has no concept of immutable variables at all.

Loop 1 to 10
Rubidium
for i in range(1, 11) {
    print(i)
}
Python
for i in range(1, 11):
    print(i)
Rust
for i in 1..11 {
    println!("{}", i);
}
C
for (int i=1; i<11; i++) {
    printf("%d\n", i);
}
Java
for (int i=1; i<11; i++) {
  System.out.println(i);
}

Rubidium's range(start, end) is exclusive of end, same as Python's and Rust's .. range — all three need 11 to cover 1 through 10. Java and C use a classic counting loop with the same exclusive bound.

    fn hit(&mut self, n: i32) {
        self.hp -= n;
    }
}

    int hp;

Rubidium has no self — fields are accessed directly by name inside a method, closer to how Java reads once you drop the implicit this. prefix (Java only needs this. when a parameter name shadows a field).

Error Handling
Rubidium
try {
    let bad: i32 = 10 / 0
} error {
    print("Error: " + error)
}
Python
try:
    bad = 10 / 0
except ZeroDivisionError as e:
    print(f"Error: {e}")
Rust
fn safe_div(a: i32, b: i32) -> Option<i32> {
    if b == 0 { None }
    else { Some(a / b) }
}
// no exceptions — Result/Option instead
C
if (b == 0) {
    printf("Error: divide by zero\n");
} else {
    result = a / b;
}
/* no exceptions — check yourself */
Java
try {
  int bad = 10 / 0;
} catch (ArithmeticException e) {
  System.out.println("Error: " + e.getMessage());
}

This is the widest split in the whole comparison. Rubidium, Python, and Java all use a try/catch-style block. Rust has no exceptions at all — errors are ordinary return values (Option/Result) the caller must explicitly handle. C has neither — you check a condition or a return code yourself, with nothing enforcing that you actually do.

Collections
Rubidium
let nums: list = [1, 2, 3]
for n in nums {
    print(n)
}
Python
nums = [1, 2, 3]
for n in nums:
    print(n)
Rust
let nums = vec![1, 2, 3];
for n in &nums {
    println!("{}", n);
}
C
int nums[] = {1, 2, 3};
for (int i=0; i<3; i++) {
    printf("%d\n", nums[i]);
}
Java
List<Integer> nums =
  List.of(1, 2, 3);
for (int n : nums) {
  System.out.println(n);
}

Rubidium's list is the direct equivalent of Python's list, Rust's Vec, and Java's List — all four iterate by value. C has no built-in dynamic array type at all; a fixed-size array is the closest primitive, with no bounds checking.

Threading
Rubidium
use thread
thread(worker(), 1)
thread.wait(1)
Python
import threading
t = threading.Thread(target=worker)
t.start()
t.join()
Rust
use std::thread;
let h = thread::spawn(worker);
h.join().unwrap();
C
pthread_t t;
pthread_create(&t, NULL, worker, NULL);
pthread_join(t, NULL);
Java
Thread t = new Thread(
  Main::worker);
t.start();
t.join();

All five give you a real OS thread and a way to block until it finishes (wait/join). Rubidium identifies threads by a plain integer ID instead of a handle object — closer in spirit to how you'd track timers, and arguably simpler for quick scripts, at the cost of losing a typed handle to pass around.

Memory model — the real difference
LanguageHow memory is managed
RubidiumNo GC, no ownership/borrow checker. Every assignment is a full deep copy. Freed manually with .drop(). The one exception is link, which shares data until a plain reassignment breaks it.
PythonAutomatic garbage collection (reference counting + cycle detector). Assignment shares references by default — mutating one name can affect another pointing at the same object.
RustNo garbage collector. The compiler enforces ownership and borrowing rules at compile time — one owner at a time, borrows checked for validity, memory freed deterministically when the owner goes out of scope.
CFully manual — you call malloc()/free() yourself. No compiler-enforced safety net; forgetting to free or freeing twice is on you.
JavaAutomatic garbage collection via the JVM (generational GC with periodic pauses). Assignment shares object references by default, same aliasing behavior as Python.

Where Rubidium sits: it avoids Python's and Java's hidden reference-sharing (deep copy makes aliasing bugs impossible by default) and avoids Rust's learning curve (no borrow checker to satisfy) — at the cost of copying data more often than a reference-based language would, and requiring the same manual discipline as C for actually freeing memory.
